# GURZÛL KHAR — Design Decision Log

This log records original linguistic and architectural decisions made under the autonomy granted in Master Development Specification v2.0 §18, with rationale and alternatives considered. All linguistic facts here must stay in sync with the JSON source of truth in `/data`.

## 2026-11-19 — Project bootstrap

### D1. Word order: SVO
**Decision:** Gurzûl Khar is a Subject-Verb-Object language with postpositional phrases (postposition `ta` "of", relativiser `kha` placed after the noun).
**Alternatives considered:** SOV (more distinct "alien" feel, closer to some real agglutinative languages) was considered but rejected for v0.1 because it increases the complexity of the deterministic translation engine (reordering constituents across three languages) disproportionately to the stylistic gain. SVO keeps clause-level reordering between English/Dutch and Gurzûl Khar minimal (noun-phrase-internal and postpositional reordering only), which keeps the engine deterministic and auditable.
**Revisit condition:** Could be revisited once the engine has a full dependency-parse pipeline rather than slot-based clause templates.

### D2. Analytic verb morphology (no person/number agreement)
**Decision:** Verbs mark tense only (`-u` present, `-ak` past, `-âth` future); person/number is carried solely by the obligatory subject pronoun or noun phrase.
**Rationale:** Removes a combinatorial explosion of conjugation tables (6 persons × 3 tenses × irregular classes) that the initial vocabulary and engine budget cannot responsibly cover with real, tested forms. An isolating verb system is linguistically well attested (e.g. Mandarin, much of creole morphology) and is not a simplification that breaks internal consistency — it is a deliberate typological choice, documented as such rather than hidden.
**Revisit condition:** A future version could add optional agreement suffixes once the lexicon and engine are mature; this would be a non-breaking additive change since pronouns would remain present.

### D3. Writing system generated procedurally from phonological features, not hand-drawn
**Decision:** The Khargûl script's glyphs are derived algorithmically from each phoneme's place/manner/voicing (consonants) and height/backness/length (vowels) as already recorded in `data/phonology/phonology.json`, rather than drawn as independent artwork per letter.
**Rationale:** (1) Guarantees "a clear relationship between characters and sounds" (spec §4.1) by construction instead of by curation. (2) Avoids duplicating the phoneme inventory in a second, hand-maintained table — the spec's data-architecture mandate (§14) to keep one source of truth. (3) Is honestly achievable with real, testable code within this project's resources, whereas commissioning 20+ bespoke glyph illustrations plus a hinted OpenType font is not.
**Known limitation (tracked in backlog):** No installable font file (OTF/TTF) exists yet; native script renders as generated inline SVG. This is sufficient for every website feature that needs native-script display but is not yet usable outside the browser (e.g. in a plain text editor).

### D4. No Tolkien Black Speech vocabulary is reused
**Decision:** Every Gurzûl Khar root, affix and function word in `/data` is an original coinage. Where the spec's own example text uses real Black Speech forms (e.g. in its historical framing), those are treated as inspiration/flavor text only and never copied into the lexicon or grammar as if they were Gurzûl Khar forms.
**Rationale:** Project requirement §2.3 and §19 — the language must be an independent fan creation, not a reproduction of copyrighted material.

### D5. Dictionary/engine/grammar reference share one JSON source of truth
**Decision:** `/data/*.json` are the only place grammatical rules, phonemes, and lexical entries are defined. The engine, the grammar reference page, and the dictionary page all read the same files; none of them hard-codes a duplicate copy of a rule.
**Rationale:** Spec §14 explicitly forbids manually duplicating language rules across website components.

## 2026-11-19 — Engine implementation (phonology/morphology/translator)

### D6. Added missing consonants "v" and "th" to the phonology inventory
**Decision:** `data/phonology/phonology.json` is extended with `v` (voiced labiodental fricative) and `th` (voiceless dental fricative, /θ/). Both already appeared constantly in `data/lexicon/lexicon.json` (e.g. "varn" to speak, "vel" tree, and the phonology file's own earlier example word "qâth" "fire") but were never declared as phonemes, so the tokenizer could not parse roughly a third of the lexicon.
**Rationale:** Spec §18's "smallest consistent extension" clause — the lexicon's own data already assumed these sounds existed; the phonology table was simply incomplete, not contradicted. Added full IPA/place/manner/voicing/position metadata consistent with the existing inventory's format. `v` is zoned to the glyph generator's "top" stem region (with bilabial/labial-velar) and `th` to "middle" (with alveolar/postalveolar/palatal), per `alphabet.json`'s placeOfArticulationRule, updated accordingly.

### D7. "ü" (diaeresis) recognised as a written variant of "û"
**Decision:** The long vowel `û` entry in phonology.json gains a `writtenVariants: ["ü"]` field. `grammar.json`'s own pronoun paradigm (`ük`, `ükûn`, 1sg/1pl subject forms) and the lexicon's matching entries use "ü", a grapheme phonology.json's vowel table never declared. Rather than rewrite the core pronoun paradigm (used throughout both grammar.json and lexicon.json consistently), the written variant is now explicitly documented as orthographically identical in sound to "û".
**Rationale:** Minimal, additive, and keeps every existing data file's spelling valid rather than picking one file to "win" over the other.

### D8. Plural epenthetic allomorph is literally "-akûk", not "root + a + ûk"
**Decision:** For roots ending in -k, the plural suffix allomorph is the fixed string "akûk" appended after the root (e.g. "rûk" -> "rûkakûk"), matching the literal parenthetical example already written in `grammar.json`'s `nouns.pluralRule` ("-akûk"), rather than a compositional "insert -a- then add -ûk" reading (which would yield "rûkaûk").
**Rationale:** grammar.json's own prose names the resulting allomorph explicitly; the engine follows that literal string so the generated form matches the one documented example to the letter.

### D9. GKH predicate/attributive adjective resolution is POS-disambiguated
**Decision:** Several Gurzûl Khar roots are deliberately homophonous/homographic across word classes by design (e.g. "khar" is simultaneously the noun "strength", the verb "to be strong", and the adjective "strong" — all legitimate word-family members of one root, per spec §6.3). When the translator needs an adjective specifically (predicate adjectives after "ash", attributive adjectives following a noun), it looks up the lexicon entry filtered to `pos: "adjective"` rather than taking whichever entry happens to be listed first for that surface form.
**Rationale:** Without this, "the king is stronger" (shak ash zan khar) rendered as "the king is more strength" because the generic lookup returned the noun entry. This is an engine-side disambiguation rule, not a change to any linguistic fact in `/data`.

### D10. Discovered inconsistency: grammar.json's complexSentenceExample gloss vs. its own tense suffix
**Finding (not changed, flagged):** `grammar.json`'s `syntax.complexSentenceExample` is `"ük zûrak sû tû pâkâth" = "I know that you will go"`. The word "zûrak" is root "zûr" + the *past*-tense suffix "-ak" (per `verbs.tenseSuffixes.past`), so the only translation consistent with the language's own documented morphology is "I **knew** that you will go" — the free English gloss in the example disagrees with the word's own suffix. The engine trusts the morphological suffix (the actual GKH data) over the explanatory prose gloss, and this regression test (`tests/regression.test.ts`, "GKH->EN complex sentence") is pinned to "I knew that you will go." This is logged here rather than silently "corrected" in grammar.json, since the example's intent (illustrating the complementiser `sû`) is unaffected either way.

### D11. EN/NL surface generation is a documented, non-exhaustive simplification
**Decision:** Rendering a GKH clause back into English or Dutch prose (`engine/translator/naturalLanguage.ts`) uses: a closed, explicit list of English/Dutch irregular past-tense and Dutch irregular-stem verb forms covering only the verbs that occur in this project's lexicon/tests; a regular-pattern fallback (`-ed`, `-s`, strip final `-en`, add `-t`) everywhere else; and analytic "more X" / "most X" comparative and superlative forms in both languages rather than attempting `-er`/`-est` or Dutch vowel-lengthening spelling changes.
**Rationale:** English/Dutch are the *interface* languages, not the conlang itself — spec §14's single-source-of-truth mandate applies to Gurzûl Khar's own grammar, not to how precisely the translator reproduces every irregular English/Dutch verb form. This is called out explicitly (here and in BACKLOG.md) rather than silently presented as complete EN/NL grammatical coverage.

## 2026-11-19 — Phase 2: alphabet redesign

### D12. Khargûl script redesigned as "Thornscript" (v0.2.0), replacing the v0.1 stem+stroke system
**Decision:** Following explicit Phase 2 direction that the v0.1 letterforms were visually unsatisfactory, three independent visual concepts were designed and shown to the project owner: Stonecarve (angular wedge strokes crossing a spine), Black iron (solid blocky shapes, no shared spine), and Thornscript (thin diagonal "thorns" branching off a spine, drawable in one continuous pen stroke). The owner selected Thornscript.
**Rationale:** Thornscript was recommended and chosen specifically because spec §4.1/§4.4 require the script to be realistically handwritable and to support stroke-order lessons; Stonecarve and Black iron both require the pen to lift and restart for most letters, while Thornscript's spine-then-thorns-then-back-to-spine path is a single stroke by construction.
**What changed:** `data/orthography/alphabet.json` bumped to v0.2.0 with new `constructionPrinciples` (spine + thorn geometry, place → zone, manner → thorn pattern, voicing → tick, vowel → thorn angle) and a new `handwriting` section (stroke order, handwritten-variant allowance). The procedural-generation philosophy from D3 is preserved — only the geometry the generator draws has changed, not the principle that glyphs are derived from phonological features rather than hand-drawn per letter. `engine/phonology/glyphGenerator.ts` was rewritten end to end to this spec (this pass), including new `generateNumeralGlyph` and `generatePunctuationGlyph` functions and a live sample-sentence rendering on the Alphabet page.
**Impact:** Every previously-rendered v0.1 glyph is visually replaced; no change to Latin transliteration, phonology, or grammar. Verified visually in a browser (no shape-dependent tests existed to break; the existing round-trip/SVG-well-formedness tests still pass unchanged).

## 2026-11-19 — Phase 2: vocabulary lifecycle, unknown-word handling, lexicon expansion, pronunciation prototype

### D13. Vocabulary lifecycle is a second JSON file (`proposals.json`), never a second copy of `lexicon.json`
**Decision:** `data/lexicon/lexicon.json` remains the single source of truth for OFFICIAL vocabulary (spec §14) — this pass does not touch that invariant. A new file, `data/lexicon/proposals.json`, holds every word that is `"proposed"` (submitted, not yet reviewed), `"deprecated"` (was official, retired, kept for history/compatibility) or `"rejected"` (reviewed and declined, kept for history). `"unknown"` is explicitly NOT a stored state anywhere — it is just what the translator reports when a word matches neither file. `engine/lexicon/mergedView.ts` is the one place that reads both files together for display purposes (Dictionary's optional lifecycle toggle); the translator and morphological analyzer deliberately do NOT read `proposals.json` at all, since an unapproved word is by definition not translatable yet.
**Rationale:** Keeps the existing single-source-of-truth guarantee for official vocabulary completely intact while still giving the four lifecycle states the brief asked for, without inventing a database or a second schema for `lexicon.json` itself.

### D14. The local "review" tool is a dev-server-only HTTP API, not a deployed backend, and unknown words fall back to a word-for-word gloss rather than failing outright
**Decision:** `website/devApi.ts` is a Vite plugin that adds `/api/lexicon/{vocabulary,suggest,propose,review,deprecate}` middleware to the Vite dev server (`npm run dev`) only. It reads/writes `lexicon.json`/`proposals.json` directly on disk with Node's `fs`. There is no authentication because there is no second user to authenticate against — whoever runs `npm run dev` on this machine IS the reviewer, which is an honest fit for "a simple local reviewer flow appropriate for a single-owner project" as the brief itself names this as acceptable. This **cannot** run in the static production build (GitHub Pages has no server process at all), so `Propose.tsx`/`Admin.tsx`/the Dictionary's lifecycle toggle all detect a failed fetch and say so explicitly rather than silently doing nothing.
Separately, the translator's unknown-word handling (`engine/translator/index.ts`) no longer fails an entire sentence just because one word is unrecognized: when the real grammar parser's only failure reason is "unknown-word", the engine now falls back to translating each recognized word directly via the lexicon (no grammatical transformation — tense/plural/word-order are not reapplied in this fallback) and brackets every unrecognized word in its original surface form, returning `ok: true, partial: true, unknownWords: [...]`. This is a deliberate, named simplification, not a second grammar engine; DESIGN_DECISIONS.md and the UI both say so.
**Rationale:** Matches the brief's explicit allowance ("If a live backend isn't feasible in this environment, implement this as data-file read/write via a minimal local dev-only mechanism") and its hard requirement that translation never silently drop an unrecognized word.
**Known limitation:** The "immediately available" requirement (approved word usable by translator/dictionary right away) holds within one running dev-server session, because the JSON files are read fresh from disk on every `/api/lexicon/vocabulary` request and the engine's own static import is only re-evaluated by Vite's module graph on the next full reload. A hard restart of `npm run dev` is the most reliable way to see an approved word picked up by the Translator page specifically (its import of `engine/data.ts` is a build-time static import, not a live fetch) — see BACKLOG.md §2 for the precise scope of what "live" means here.

### D15. Lexicon expansion (133 → 292 entries) kept every new word inside the already-declared phoneme inventory and phonotactic rules
**Decision:** New entries across people/relationships, time/space, emotions, power/hierarchy, warfare, crafts/materials, everyday life, abstract concepts and additional nature/descriptive vocabulary were deliberately built from single onsets/codas (never a word-initial or word-final consonant cluster outside the documented allowed lists) so that none of them add new entries to the existing 15-item phonotactic-review warning list. Two mistakes made while drafting (accidental word-initial "zh" in three words, two disallowed "-lm" codas) were caught by `npm test` and fixed before committing.
**Rationale:** The brief asked for quality over quantity and explicit phonotactic correctness per new entry; re-running the existing (not forked) phonotactic checker during drafting was the mechanism for actually enforcing that, not just claiming it.

### D16. Rule-based Web Audio pronunciation prototype is additive and explicitly experimental, not a TTS replacement
**Decision:** `website/src/lib/audioSynth.ts` renders a word's phoneme sequence (from the same tokenizer/syllabifier as the rest of the site) as oscillator tones (vowels, pitch keyed to vowel quality) and filtered-noise/tone bursts (consonants, keyed to manner/voicing) using the Web Audio API — fully offline, non-neural, deterministic. It is a second, separately-labelled "experimental" button on the Pronunciation page, not a replacement for the existing SpeechSynthesis aid.
**Rationale:** The brief explicitly asked to investigate this and to document honestly if it could not be made real; this prototype is real and functions (verified in-browser with no console errors), but it does not model coarticulation, assimilation, or real formant structure, and is labelled as such rather than oversold as "how Gurzûl Khar sounds."

### D17 (process note). `Phase2.md` was not present in the repository when this pass began
**Finding:** The task brief for this pass referenced `Phase2.md` as the authoritative source document, but no such file existed anywhere in the repository (confirmed by a recursive search) — only `BACKLOG.md`, `DESIGN_DECISIONS.md`, the Master Development Specification, and the detailed task description supplied directly to the agent for this pass. This pass proceeded from that supplied task description, since it was itself represented as a faithful translation of `Phase2.md`'s brief into concrete scope. Recorded here so the project owner can reconcile this with whatever they intended `Phase2.md` to contain, and add it to the repository if it should exist going forward.

## 2026-11-24 — Phase 3/4: the Rust port and the WebAssembly build

### D18. The Rust core has zero dependencies, because the data is generated into it rather than parsed at runtime
**Decision:** `crates/gkh-core` depends on nothing — not `serde`, not `once_cell`, not `regex`. `scripts/buildRustData.mjs` reads `data/*.json` and emits Rust source (`src/data/generated.rs` and friends) containing plain `const` arrays of `&'static str` tuples, plus the test fixtures as Rust constants. The crate `include!`s those files.
**Alternatives considered:** `serde` + `include_str!` + a `OnceLock<Lexicon>` is the obvious shape and was rejected. It drags a derive-macro dependency tree into a crate that must compile to WebAssembly and later into an Android binary, it moves parsing to runtime (so a malformed data file becomes a panic on a user's phone rather than a failed build), and it would have made the wasm artifact several times larger for no behavioural gain.
**Consequence:** the data is compiled in, so a stale generated file is a real failure mode. `.github/workflows/rust.yml` regenerates the data and fails the build if the checked-in copy differs, which is what keeps `data/` the single source of truth (D5) across two languages.

### D19. Both engines are held to the same shared fixtures, not to each other's code
**Decision:** correctness of the port is defined as "produces the same output as the TypeScript engine on `tests/fixtures/*.json`", and both suites read those files. The Rust side gets them as generated constants; Vitest reads the JSON directly. Nothing in the Rust port is verified by reading the TypeScript and agreeing it looks equivalent.
**Rationale:** this is the only mechanism that keeps two implementations honest while both exist, and it is the reason phase 1 (fixtures + the 10,549-case golden file) was done before any Rust was written. It worked: the fixtures caught a genuine divergence in the translator's refusal logic (D20) that reading both files side by side had not.

### D20. The translator falls back word-for-word only on unknown vocabulary, never on unsupported grammar
**Finding and fix:** after all 52 shared cases passed, manual probing found that the Rust translator answered "the sword that he carries" word-for-word while the TypeScript one refused it. Both engines fall back when a word is unknown (D14); only TypeScript was also distinguishing that from an unsupported *pattern*, which must fail honestly (an object-gap relative clause is grammar the language does not yet have, not a missing word). `crates/gkh-core/src/translator/translate.rs` now tracks the last failure reason and falls back only for `UnknownWord`, and the fixture for that sentence was tightened so the distinction is pinned rather than remembered.
**Worth recording:** this is the one divergence the fixtures did not catch on their own — the case existed but asserted too weakly. A fixture that only asserts "fails" is not a test of *why* it fails.

### D21. The website selects its engine at build time, with a runtime fallback
**Decision:** `website/src/engine/` defines one `Engine` interface with two implementations. `vite.config.ts` reads `GKH_ENGINE` and aliases `@wasm` either to the compiled crate or to a stub that throws `NOT_BUILT`, so the site builds and runs normally when no WebAssembly artifact is present. `initEngine()` runs before React mounts and falls back to the TypeScript engine if the wasm module fails to load.
**Rationale:** a build-time switch keeps the wasm artifact out of the default bundle entirely rather than shipping a dead code path, and the runtime fallback means a broken or missing artifact degrades to the working engine instead of a blank Translator. ROADMAP.md's phase 4 gate — delete the TypeScript engine — is deliberately not met by this pass: the replacement is not yet proven in a browser on a real wasm build.

### D22. The coiner's hash contract survived the port intact, and two details in it are load-bearing
**Finding (recorded because both are easy to "clean up" and silently catastrophic):** `coiner_v1` sub-seeds each decision with `hash(format!("{root:016x}:{label}"))`. The zero-padding to 16 hex digits is part of the hash input, so dropping it would reshuffle every coined word ever produced. Separately, the minimum-length check counts *characters*, not bytes — `gkh.chars().count() < 2` — because `û` and `â` are two bytes each in UTF-8 and a byte-length check would accept one-character words. Both are pinned by the golden file, but neither is obvious from reading the code, so they are written down here.
